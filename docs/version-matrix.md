# Version Matrix

This document is non-normative. It maps specification versions to the reference implementations and the conformance profiles each one claims, so an evaluator can tell at a glance which artifact implements which version of the protocol and where that claim is verified. The authoritative versioning policy is [VERSIONING.md](../VERSIONING.md); dated release notes are in [CHANGELOG.md](../CHANGELOG.md).

## Reading the rows

**Spec v0.1.0 (Final).** The contents of this repository's `main` branch: RFCs 0001–0008 at status Final, RFC-ACDP-0009 reserved, the JSON Schemas under `schemas/json/`, and the conformance fixtures under `schemas/conformance/`. v0.1.0 is wire-frozen — clarification rounds add prose and fixtures, never wire changes.

**Spec v0.2.0 (Final).** Merged on `main` as Draft (2026-07-04) and promoted to **Final** on 2026-07-05 per RELEASE.md, the conformance pack having passed against two independent interoperating implementations (`acdp-rs` and `acdp-verifier-py` — see CHANGELOG.md). It is a backward-compatible minor version: every v0.1.0 body, signature, and `content_hash` remains valid. Headline additions: RFC-ACDP-0010 registry receipts (registry-signed binding of `ctx_id` / `lineage_id` / `origin_registry` / `created_at` / `content_hash` / producer-key fingerprint, closing the RFC-ACDP-0008 §9.1 registry-honesty gap for receipt-bearing responses), `did:key` producers, the hash-divergence corpus (`can-012`), and the `acdp-registry-receipts` profile. One parse-surface caveat: the previously closed publish response gains the OPTIONAL `registry_receipt` member.

**`acdp-rs` (reference SDK — producer, consumer, verification core).**

- `0.1.x` implements spec v0.1.0: the `acdp-consumer` profile (client, `WebResolver`, `CrossRegistryResolver`, strict verification) plus the producer and server-side validation building blocks.
- `0.2.x` implements the spec v0.2.0 surface (then Draft): receipt minting/verification (RFC-ACDP-0010), `did:key` resolution, divergence diagnostics, and the explicit-`acdp_version` builder default.
- `0.3.x` is the same v0.2.0 protocol surface refactored into a fine-grained Cargo workspace; no wire-visible change.
- `0.5.x` implements the spec v0.2.0 + v0.3.0 Final surface plus the v0.4.0 RFC-ACDP-0015 witness-cosigning types: require-mode conformance passes the executed `rcpt`/`lhr`/`log`/`rev`/`wit` bindings.
- `0.8.x` through `0.19.x` (crates.io `acdp 0.19.0`, current) carry that same Final surface on the current workspace layout, plus the Draft 0.5.0 additions, which arrived incrementally: `anchors` types from `0.8.2` (bindings `0.8.3`), typed `unsupported_media_type` from `0.13.2`, the revocation rejections from `0.14.0`. Strict Ed25519 verification (`verify_strict`, rejecting non-canonical `s` and small-order `A`/`R`) is in the core from `0.14.4`. `0.15.0` is a breaking SDK release (see its [migration guide](https://github.com/agentcontextdistributionprotocol/acdp-rs/blob/main/docs/migrating-to-0.15.md)) that adds the *(0.5.0)* consumer-verification amendments: revocation `unknown` reported as its own verdict, never folded into not-revoked (RFC-ACDP-0014 §7/§8), `bearer_jwt` read authentication on the client (RFC-ACDP-0008 §6.2), and opt-in transparency-log and witness verification, where a log proof without a verified receipt is "cannot verify", not `invalid_log_proof` (RFC-ACDP-0012 §9.1). `0.15.1` reports a malformed registry response as `schema_violation` per RFC-ACDP-0007 §3.3.1 (see [`errors.md`](https://github.com/agentcontextdistributionprotocol/acdp-rs/blob/main/docs/errors.md)). Later releases add the remaining *(0.5.0)* surfaces: offline chain verification (`acdp-chain`, RFC-ACDP-0017) from `0.16.1`, trust lists (RFC-ACDP-0020) and the MCP signing proxy (`acdp-mcp-proxy`, RFC-ACDP-0019) from `0.17.3`, and keyless signing behind the `keyless` feature (RFC-ACDP-0021) from `0.18.0`, at draft.4 from `0.18.3`. The language bindings are tagged and published in lockstep with the crate (`acdp-node` on npm as `@agentcontextdistributionprotocol/acdp`, `acdp-wasm` on npm as `@agentcontextdistributionprotocol/acdp-wasm`, `acdp-py` on PyPI as `acdp`, all **0.19.0**); their toolchain floors are in [`bindings.md`](https://github.com/agentcontextdistributionprotocol/acdp-rs/blob/main/docs/bindings.md#pinned-binding-toolchain). Per-release detail lives in the SDK's own changelog and [`docs/`](https://github.com/agentcontextdistributionprotocol/acdp-rs/tree/main/docs) (e.g. `producing.md`, `consuming.md`, `errors.md`) — not repeated here.

*Where conformance is verified:* the SDK's own conformance suite (`tests/conformance.rs`) executes the spec's golden vectors and fixtures directly — point `ACDP_SPEC_DIR` at a checkout of this repository (the matching branch for 0.2.x/0.3.x) and run `cargo test --test conformance`. The suite skips silently when `ACDP_SPEC_DIR` is absent — set `ACDP_REQUIRE_CONFORMANCE=1` (as the SDK's conformance CI job does) to turn a missing spec checkout into a hard failure, so a green run proves the fixtures actually executed. That CI job checks out a specific commit of this repository; see ["The pinned spec ref"](https://github.com/agentcontextdistributionprotocol/acdp-rs/blob/main/docs/conformance.md#the-pinned-spec-ref).

**`acdp-registry-rs` (reference registry).** Implements the spec as a running service: it advertises the `acdp-registry-core` and `acdp-registry-discovery` profiles by default, and — with a `[receipt]` signing key configured — the v0.2.0 `acdp-registry-receipts` profile (signed, atomically-persisted publish receipts, self-hosted `did:web` document, `did:key` producers). Current `main` serves all three v0.3.0 profiles (`acdp-registry-head-receipts`, `acdp-registry-transparency-log`, `acdp-registry-lifecycle`) end-to-end. It also aggregates RFC-ACDP-0015 witness cosignatures, serving verified ones as the `witness_signatures` member on transparency-log checkpoints (0.4.0). Cross-registry retrieval of foreign `ctx_id`s is available as a feature, but the registry does not currently claim the `acdp-registry-federated` profile. Its configuration and HTTP surface (including how the 0.5.0 `anchors` gate and `acdp_version` advertisement work) are documented in the registry's own [`CONFIGURATION.md`](https://github.com/agentcontextdistributionprotocol/acdp-registry-rs/blob/main/docs/CONFIGURATION.md) and [`HTTP-API.md`](https://github.com/agentcontextdistributionprotocol/acdp-registry-rs/blob/main/docs/HTTP-API.md). Read authentication (the DID challenge-response flow, and the `bearer_jwt` method it advertises when `auth.enabled = true`) is documented in its [`AUTHENTICATION.md`](https://github.com/agentcontextdistributionprotocol/acdp-registry-rs/blob/main/docs/AUTHENTICATION.md); the spec side is RFC-ACDP-0008 §6.2 and [registries/auth-methods.md](../registries/auth-methods.md).

**`acdp-verifier-py` (second, independent implementation).** The verification-only cross-check that the two-implementation promotion gate relies on. It pins a specific commit of this repository as its spec reference and executes the arithmetic vectors and the structural/validation consumer-side fixtures; SSRF/transport families and fixtures that need a live registry (e.g. `fed-*`, `rev-003`/`rev-004`) are registered as skips. Its pinned spec ref is the authority on which spec revision it has been checked against. It currently pins `1560e0f` and executes the *(0.5.0)* consumer fixtures, including strict Ed25519 verification (RFC-ACDP-0001 §5.10, vector `sig-004`) and the RFC-ACDP-0017, RFC-ACDP-0020 and RFC-ACDP-0021 consumer fixtures; its [README](https://github.com/agentcontextdistributionprotocol/acdp-verifier-py#readme) gives the exact pass and skip set.

*Where conformance is verified:* the registry's own harness (`crates/acdp-registry-server/tests/conformance.rs`) executes the behavioral fixture families (`pub-*`, `vis-*`, `ret-*`, `idem-*`, …) against a live in-process registry — the half of the suite that `scripts/conformance-runner.py` in this repo deliberately does not execute (it runs only the arithmetic/cryptographic vectors — `can-*` / `lin-*` / `sig-*` / `fp-*` and the keypair-bearing `rcpt-*` / `lhr-*` / `log-*` / `wit-*` / `rev-*` goldens; see [schemas/conformance/README.md](../schemas/conformance/README.md)).

## Rules of thumb

- Pinning a library? `acdp = "0.1"` gives you frozen v0.1.0 semantics; `0.2`/`0.3` carry the v0.2.0 surface; `0.5` and later carry the v0.2.0 + v0.3.0 Final surface plus the v0.4.0 witness-cosigning types — the current release is `0.19.0` across crates.io, npm, and PyPI (full family lockstep).
- Talking to a registry? Read its `/.well-known/acdp.json`: `acdp_version` and `profiles` are the authoritative statement of what it implements — not this table.
- Writing a new implementation? Target v0.4.0 (Final; v0.1.0/v0.2.0/v0.3.0 remain Final and wire-frozen); treat anything marked *(0.5.0)* as Draft and subject to change; the optional 0.2.0/0.3.0/0.4.0 surfaces (receipts, `did:key`, head receipts, transparency log, lifecycle, witness cosigning) are profile-gated — adopt them as you need them.
